# Test strategy

## Summary

Automated tests are written with the change they cover, in the same pull
request, and CI runs them before merge. The engine (`core`) is tested with
GoogleTest and CTest, targeting 70% line coverage. The app (`ui`) is tested with
Vitest, targeting 50% line coverage. A manual beta test plan covers what
automation does not. This document replaces
[`testing-policy-core.md`](testing-policy-core.md) and extends it to `ui`.

Facts below were gathered on 2026-10-29 from the repositories and their CI
workflows. Coverage numbers are in the [coverage report](coverage-report.md).

## Which test for which part

| Part | Test type | Tool | Run by |
| --- | --- | --- | --- |
| Engine components (file parsing, signal processing blocks, tag writing) | Unit | GoogleTest | CI, locally |
| Engine as a whole, from input file to output file | Integration | GoogleTest | CI, locally |
| App logic without Electron (state, formatting, path handling, metadata service, tag write queue) | Unit | Vitest | CI, locally |
| App against the real compiled addon | Integration | Vitest | CI, locally. Added through [ui#88](https://github.com/Dissonance-Eip/ui/issues/88) |
| App screens and flows | Manual beta | [Acceptance test plan](acceptance-test-plan/README.md) | Testers, on released installers |
| Protection effectiveness and audibility | Measurement, not a pass or fail test | The [`Tester`](https://github.com/Dissonance-Eip/Tester) harness | Maintainers, manually |
| Code style and static analysis | Gate | clang-format and cppcheck (`core`), ESLint and Prettier (`ui`) | CI |

Rule of thumb: put the test at the lowest level that can fail for the reason
you care about. Use an integration test when the bug could only appear when
parts are combined, as with the engine pipeline or the app with the addon.

## Where tests live

| Repository | Folder | Framework | Count on 2026-10-29 |
| --- | --- | --- | --- |
| `core` | `core/tests/` | GoogleTest, run through CTest | 106 test cases in 12 files (count of `TEST`, `TEST_F` and `TEST_P` macros) |
| `ui` | `ui/tests/` | Vitest | 45 test cases in 5 unit test files, plus the addon integration test being added |

Tests are not placed next to the source. Each repository keeps one flat
`tests/` folder.

Test audio is generated by the tests, never committed. `core/tests/support/`
holds the shared helpers that build the signals. Audio files must not be
committed to any repository.

## Naming

- `core`: file `<subject>_test.cpp`, GoogleTest suite `<Subject>Test`, test
  name describes the expected behaviour, for example
  `WavRoundtripTest.StereoSampleCountCorrect`.
- `ui`: file `<ModuleUnderTest>.test.js`, named after the module, with
  `describe` blocks per behaviour. The integration test is named
  `*.integration.test.js`.
- A test name says what must hold, not how it is built.

## When tests are written

- With the pull request, before merge. A pull request that changes behaviour
  adds or updates tests in the same pass.
- A bug fix adds a test that fails without the fix.
- Tests are deterministic: no unseeded randomness, no dependence on machine
  speed or on files outside the repository.
- Tests that open files close them before deleting them, so that they pass on
  Windows as well as on macOS and Linux.

## Coverage targets

| Repository | Target (lines) | Command | Enforced in CI |
| --- | --- | --- | --- |
| `core` | 70% | `npm run coverage` (CMake option `ENABLE_COVERAGE`, gcov or llvm-cov) | No. A CI job writes the total to the job summary |
| `ui` | 50% | `npm run test:coverage` (Vitest with the V8 provider) | No |

The issue proposed 80% for `core` as a starting point; the team set 70%.
The engine has the higher target because it is the critical part. The `core`
coverage run measures `src/` only, and reports sources not linked into the test
binary (the CLI and the addon glue) as not measured. TODO(team): decide whether
and when to make coverage a failing gate.

## CI gates

| Repository | Workflow | Checks |
| --- | --- | --- |
| `core` | `core/.github/workflows/ci.yml` | cppcheck on `src/` (fails on findings), clang-format check, CMake build and CTest, coverage summary |
| `core` | `core/.github/workflows/release-addon.yml` | On a tag: addon build on three platforms and a load check that the addon exports `process` |
| `ui` | `ui/.github/workflows/ui-quality-checks.yml` | `npm run lint`, `npm run format:check`, `npm test`, `npm run build` |

Before opening a pull request, run the same checks locally. The commands are in
[`CONTRIBUTING.md`](../CONTRIBUTING.md). Merge rules are in
[`GOVERNANCE.md`](../GOVERNANCE.md).

## Known gaps

- The mentor asked for a check of external input validation and of the app's
  behaviour when the engine is unavailable. TODO(team): list the existing tests
  for these, or open issues to add them. This document does not claim they
  exist.
- `core` CI builds on Linux only, while releases build on three platforms.
- No test runs the packaged installer. That is covered by manual beta testing.
